## Finding

**OBSERVED:** the owner's report is explained by the source. The frontend's Details mode is GUI.Forms `ObjectView` with a name region and one heterogeneous `secondary_text` region. These are two painted regions, not two configured factual columns. There is no header, column identity, cell model, header activation, width manipulation, or horizontal column scrolling in this public control. The secondary field is a size for ordinary files, `Folder` for directories, and a link/object description for other entries. A label such as “Size” above that field would misrepresent its contents.

**GIVEN:** the current audit assignment reports the owner's requirement for the planned headers and rejection of the two-column result. Earlier owner verdicts independently accept compact aligned metadata and file attributes as first-class sortable columns. **OBSERVED:** I did not recover a selected default column set or ordering from the checked-in records searched below. The question atlas explicitly asks which keys and column persistence policies to choose. Do not describe Name/Kind/Size/Modified as the owner's selected set merely because those four sort commands currently exist.

**CANDIDATE:** extend the public shared `ObjectView` with a real Details column/cell projection while keeping its stable selection model and icon presentation. The smallest useful factual specimen can use already available name, kind classification, regular-file length, and modification time, subject to an explicitly recorded provisional column choice. Header labels, unavailable values, and sorting must describe those exact facts. Implementing an application-private table or drawing headers over the existing two text regions would leave the reusable control and accessibility gap unresolved.

## House-style source review and audit limits

The governing standard is [the complete Programming House Style](../../planning/PROGRAMMING_HOUSE_STYLE.md). This audit authored only this Markdown file; no implementation, tests, scripts, generated code or vendored dependencies were changed. No scanner result is offered as style evidence.

**Exact source-review scope:** complete `ObjectView` public header; implementation model replacement, selection, mode/geometry/scroll, paint/elision, input and semantic functions; complete `object_order.hpp`; frontend construction, mode/order setters, directory projection and settings application identified above; filesystem entry/identity declarations and enumeration/modified-display paths; listed test assertions. This is a focused review, not certification of the complete application, filesystem platform adapters, semantic host adapters, tests, or legacy toolkit.

**Remaining violations/risks observed within that scope:**

- `ObjectView::item_id_at` uses `const auto index` (implementation line 602), contrary to explicit local types. Geometry helpers such as `columns`, `row_height` and `item_bounds` return calculated expressions/constructed results rather than named calculated values. These need direct source review when touched; spelling compliance alone would not close the following issues.
- `ObjectViewItem` string fields and several local aggregates such as `ObjectSelectionChange change`, `IconLabelLayout result`, `SemanticDescriptor descriptor` and `SemanticNode node` omit explicit initializer spelling. Standard class default construction is not uninitialized string storage, but it does not follow the owner's explicit-initialization form.
- `elide_object_name` constructs candidate strings repeatedly while probing grapheme fits; icon paint constructs label vectors/strings per visible item; `type_select` folds each item name into a temporary string in its search loop. Repeated-layout/storage work remains to be reviewed and measured; new cell formatting must not repeat this pattern across every column on every paint.
- `set_items` validates the incoming model before replacing it, but replaces `items_` before rebuilding retained selection storage. Allocation failure during that rebuilding can leave replacement state partly updated; the strong/partial failure guarantee is not documented. A column/cell extension needs a specified transactional publication guarantee, not an assumed one.
- `item_bounds` subtracts `top_row_` from an unsigned row. Visible paint callers satisfy the ordering, but semantic actions can target unrealized items; coordinate derivation must explicitly establish visibility or use safe signed differences. Header offset work must not copy unchecked unsigned geometry arithmetic.
- Ownership of rows is explicit in `ObjectView`; image-list subscription uses a named member target and token; sort comparators borrow the entry map synchronously and select mode before comparison. These are useful retained patterns, not blanket compliance claims. Full application callback lifetime/teardown is outside this review.
